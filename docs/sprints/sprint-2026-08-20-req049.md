# Sprint „Operable" — 2026-08-20 → 2026-09-03 (REQ-049)

## Sprint story (goal)

> **A Romanian SMB owner can sign up, set up their company, issue an invoice and
> submit it to ANAF without ever hitting a dead end — and the DocumentIulia team
> has a staff back-office where they see every client, answer every client
> request, and manage every account.**

Two sides of the same coin: the **client side** must be *fully usable* (no broken
links, no fabricated data, no dead-end journeys), and the **staff side** must
exist at all (today there is no console to operate client requests).

**Inputs:** REQ-048 review backlog (63 verified findings, waves 1–3 shipped),
expert-consortium review `wf_5a18e6ba-e30` (7 experts, running — folded in via
story C1), CLAUDE.md expert-team protocol.

**Capacity assumption:** autonomous agent, ~55 SP. Must = 39 SP.

## EPIC A — Staff Back-Office (`/dashboard/admin`)

*As a DocumentIulia staff member, I need one place to see clients, operate their
requests, and manage their accounts, so client operations stop depending on
direct database access.*

### A1 — Admin backend module · **Must · 8 SP**
*As staff, I can find any client and see their whole situation.*

**To-dos**
- [ ] `backend/src/admin/` module: `AdminController` + `AdminService`, guarded `JwtAuthGuard + RolesGuard @Roles(ADMIN)` (staff-wide read; mutations ADMIN-only)
- [ ] `GET /admin/overview` — KPIs: users total/new-30d, orgs, invoices count+value 30d, e-Factura submissions, open tickets
- [ ] `GET /admin/clients?search=&tier=&role=&page=` — paginated user+org list (email, company, CUI, tier, role, createdAt, lastActivity from AuditLog)
- [ ] `GET /admin/clients/:id` — client-360: profile, organization, subscription/tier, last 10 invoices, e-Factura statuses, last errors from error log, open tickets
- [ ] `PATCH /admin/clients/:id` — tier/role/isActive changes, **every change writes an AuditLog row**
- [ ] Jest: guards deny USER role; 360 aggregates correctly; audit row on patch
- **AC:** staff finds any client by email/CUI in <2 clicks; USER role gets 403 on all `/admin/*`.

### A2 — Client requests (ticket system) · **Must · 8 SP**
*As a client, I can ask for help from my dashboard; as staff, nothing lands in a void.*

**To-dos**
- [ ] Prisma: `SupportTicket` (id, userId, subject, category, status `OPEN|IN_PROGRESS|WAITING_CLIENT|RESOLVED|CLOSED`, priority, assignedToId?, createdAt/updatedAt) + `TicketMessage` (ticketId, authorId, isStaff, body, createdAt); migration
- [ ] Client endpoints: `POST /support/tickets`, `GET /support/tickets` (own), `POST /support/tickets/:id/messages`, reopen
- [ ] Staff endpoints: `GET /admin/tickets?status=&assigned=`, `PATCH /admin/tickets/:id` (status/assign/priority), `POST /admin/tickets/:id/messages` (isStaff=true)
- [ ] Wire the public **/contact form** → creates a ticket (guest email captured) instead of going nowhere
- [ ] Client UI: „Ajutor / Cererile mele" page — new request + thread view
- [ ] Jest on ownership scoping (client sees only own tickets)
- **AC:** contact-form submission appears in the staff inbox; client sees staff reply in their thread; status transitions audited.

### A3 — Staff frontend section · **Must · 8 SP**
*As staff, the console is one place: overview → clients → requests → tools.*

**To-dos**
- [ ] Role-gated layout `/[locale]/dashboard/admin` (hide nav entry + client-side redirect for non-staff; server relies on 403s)
- [ ] `admin/page.tsx` — overview KPIs + open-ticket count + newest clients
- [ ] `admin/clients/page.tsx` — searchable table (email/company/CUI/tier/status)
- [ ] `admin/clients/[id]/page.tsx` — client-360 with tier/role editing (confirmation dialog, reason field → audit)
- [ ] `admin/requests/page.tsx` — ticket inbox: filter by status/assignee, thread panel, reply, status buttons
- [ ] „Tools" rail linking existing staff surfaces: CRM, error-logs page, security audit, monitoring
- [ ] RO diacritics correct throughout; loading/empty/error states on every view (no fabricated placeholders)
- **AC:** a staff member resolves a real ticket end-to-end in the UI; a USER never sees the section.

### A4 — CRM as client-operations tooling · **Should · 5 SP**
*As staff, client requests connect to the CRM record of that client.*

**To-dos**
- [ ] Link `User ↔ CRM Contact` (nullable `contactId` on User or lookup-by-email service)
- [ ] "Create CRM activity from ticket" action (staff inbox → activity on the linked contact)
- [ ] Client-360 shows linked CRM contact + last activities; create-link button when none
- **AC:** ticket → CRM activity in one click; the activity references the ticket id.

### A5 — Subscription management for staff · **Should · 5 SP**
*As staff, I can see and change what a client pays for — and the plan actually gates something.*

**To-dos**
- [ ] Audit what tier currently enforces (subscription module + guards) — document in `docs/architecture/tier-enforcement.md`
- [ ] Client-360: subscription card (plan, period, source: manual/Stripe) + change-plan action (audited)
- [ ] Reconcile the **billing page** (client side) to real subscription data — kills one fabricated page (B2 overlap)
